# 注释与 Markdown 编写规范

本文规定本项目文档和源码注释的写法，目标是让内容面向维护者、可检索、可验证，并能在代码变化后持续更新。新建或修改文档、注释时遵循本规范。

## 写作原则

- 以读者完成理解或维护任务为目标，陈述事实、规则、原因和操作步骤。
- 使用准确、简洁、客观的表达。避免聊天语气、口头禅、感叹、反问和过程记录。
- 不写“我觉得”“我发现”“我们这里”“AI 已经”等第一人称或写作过程描述。需要表达项目决策时，写明决策本身及适用范围。
- 先给结论或用途，再补充背景、条件和例外。一个段落围绕一个主题。
- 术语、模块名、配置项、接口、路径和代码标识符使用项目中的正式名称，并用反引号标记代码标识符。
- 不重复代码或邻近章节已经说明且不会帮助读者理解的信息。

## AI 开发任务的时限

AI 在执行开发任务前，必须为每个可能持续等待的步骤设置明确的超时时间，并在开始前告知用户预计时限。不得启动无期限的构建、测试、安装、网络请求、工具调用或进程等待。

- 将较大的任务拆分为可检查的小步骤，为每一步设定时限；总任务较长时，设定阶段检查点并及时汇报进度。
- 构建、测试和依赖安装应使用工具支持的超时参数。交互式或后台进程应定期检查状态，并设置整体截止时间；不要用长时间无反馈的阻塞等待。
- 时限应结合任务规模和工具特性合理设置，明确写出数值和单位。短命令使用较短时限；大型构建可给出较长时限，但应分阶段观察，不应一次等待几十分钟而不检查。
- 步骤达到时限仍未完成时，应停止或安全地中断该步骤，记录已获得的输出，检查进程是否仍在运行，并先判断是正常耗时、资源不足、网络等待还是死锁/卡死迹象。
- 只有在确认仍有合理进展且可以解释原因后，才可调整时限重试一次；重试前说明新的时限和依据。连续超时、无进展或无法安全中断时，停止重复尝试，汇报现象、已检查信息及需要的后续处理。
- 不得在超时后静默地无限重试、另起重复进程或把仍在运行的任务报告为已完成。最终说明实际耗时、结果或阻塞原因。

## 源码注释

### 何时添加

- 解释意图、约束、非显然的业务规则、兼容性要求、边界条件或规避方案。
- 解释代码本身无法清楚表达的副作用、线程/生命周期要求、单位、取值范围或调用顺序。
- 对外 API、复杂算法和公共类型补充调用方需要的契约说明。
- 不为显而易见的赋值、分支、循环或 getter/setter 添加逐行旁白。

### 如何编写

- 注释应说明“为什么”或“必须满足什么”，而不是复述“代码做了什么”。
- 注释与所描述的代码保持相邻；范围较大的说明放在类型或模块文档中。
- 使用完整、清晰的句子，标点统一。中文注释使用中文标点；代码标识符、路径和命令保持原样。
- 注释必须与当前实现一致。修改行为时同步检查相关注释，删除过时说明。
- `TODO`、`FIXME` 等待办标记应写明事项和可识别的上下文；有对应 issue 时附链接或编号。禁止留下无说明的待办标记。
- 不在注释中记录临时调试过程、个人感受、提交日志或未经确认的猜测。

## Markdown 文档

### 结构

- 每份文档以唯一的一级标题开头，标题准确描述主题。
- 使用层级连续的标题组织内容：一级标题后按需使用二级、三级标题，不跳级，不以加粗文本代替标题。
- 先写用途、适用范围和必要前提，再写步骤、细节、示例、限制或参考资料。
- 操作步骤使用有序列表；并列事项使用无序列表；字段对照或选择比较使用表格。
- 代码、命令、配置示例使用带语言标识的围栏代码块；行内标识符使用反引号。
- 链接文字应能说明目标内容。相对链接优先指向仓库内文件，并确认目标存在。

### 表达与格式

- 用简体中文说明项目内容；技术名词、API 名称和代码标识符按官方或项目写法保留。
- 中文与英文、数字之间加一个半角空格，例如「TCP 端口 44444」「耗时 3.5 秒」；中文句子使用全角标点，路径、命令与代码标识符保持原样。
- 段落简短且主题单一。需要表达条件、结果和例外时写清它们之间的关系。
- 列表项保持语法平行，句式和标点风格一致。完整句以句号结束；短语列表统一不加句末标点。
- 表格单元格保持简洁；复杂说明放到表格外。
- 不使用无意义的“如下”“见上”等依赖阅读位置的表达；给出明确标题或链接。
- 图片应提供有意义的替代文本，并确认相对路径有效。

## 可维护性与事实管理

- 标注会影响操作的前置条件、适用版本、默认值和失败处理；不确定的信息应先核实，不以推测写成事实。
- 版本号、日期、命令、路径、接口字段和配置值应从当前项目状态核对。
- 避免复制维护同一事实；需要跨文档引用时链接到唯一权威说明。
- 文档应描述当前有效行为。历史背景仅在解释当前约束或迁移路径时保留，并注明时间或适用版本。
- 变更完成后检查目录、标题、链接、代码围栏和示例是否仍然有效。

## 用语对照表

写作与改稿时，避免左列的口语、网络用语，按语境改用右列的书面表述：

| 口语表达 | 规范表述 |
| --- | --- |
| 兜底 | 后备处理、缺省逻辑、异常保护 |
| 踩坑、踩过的坑、坑 | 已知问题、注意事项 |
| 卡死、卡住 | 阻塞、失去响应；确认为死锁时写「死锁」 |
| 卡在 | 停留在、阻塞于 |
| 干掉、杀掉 | 终止、删除、结束进程 |
| 踢、踢下线、被踢 | 强制断开连接、断开连接 |
| 塞进、塞回、怼、扔进 | 写入、传入、放入 |
| 丢进、丢给 | 移交、传递；数据丢失场景写「丢失」 |
| 砍掉、拔掉 | 移除、停用 |
| 跑通、跑一遍、跑过 | 验证通过、执行一次、已运行 |
| 起服、起服务、起不来 | 启动服务器、无法启动 |
| 停服 | 停止服务器 |
| 关掉、开着 | 停用、关闭、保持启用 |
| 开权限 | 授予权限 |
| 写死 | 硬编码 |
| 照抄 | 沿用、复制 |
| 省得、省事 | 避免、以便 |
| 瘦包 | 精简包 |
| 搞定、弄好、搞 | 完成、处理 |
| 老服、老的 | 旧服务器、旧版本 |
| 撑爆、吃掉 | 超出上限、占用 |
| 对表 | 对照、核对 |
| 摸清、摸一下 | 确认、检查 |
| 压成一行 | 合并为单行 |
| 崩了、崩在 | 崩溃、崩溃于 |
| 炸了 | 出现异常、失败 |
| 顺手、顺带 | 同时、一并 |
| 打死不能 | 禁止 |
| 别 | 不应、不要 |
| 咱、你、我 | 删去主语，改为陈述句 |

对照表无法穷尽所有口语表达；拿不准时按「书面、客观、可验证」的标准改写。

## 提交信息

- 使用中文 Conventional Commits 格式：`<type>(<scope>): <简述>`，`type` 取 `feat`、`fix`、`docs`、`refactor`、`perf`、`test`、`build`、`ci`、`chore`。
- 简述不超过 50 字，写明变更点，不使用「更新」「优化」等无信息量的表述，不加句号和 emoji。
- 正文说明原因与影响，不记录工作过程；有实测结果时附实测说明，未验证的写明「未验证」。
- 提交信息同样遵循用语对照表。
- 已推送的历史提交不做改写，规范只约束后续提交。

## 提交前检查

- 内容是否面向读者，而非记录作者或 AI 的工作过程？
- 注释是否解释必要的意图或约束，且与实现一致？
- 是否已清除用语对照表中的口语表达？
- 标题层级、列表、表格、代码块和链接是否规范？
- 文中的版本、路径、接口和命令是否已核对？
- 是否存在重复、过时、含糊或无法执行的说明？
